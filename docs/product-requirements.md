# Fieldnote 行业调研Agent · 产品需求文档

版本：v0.1.1（文档补齐）；更新：2026-11-25。

产品状态：探索性可分享原型，真实模型与现场研究待验证。下文区分已实现、待验证和规划。

## 1. 命题与目标用户

通过通用知识搜集和专项调研，理解垂直行业中的真实AI应用，覆盖使用流程、决策因素、行业/组织策略、用户心理及其他实际影响因素。研究结论应可追溯、可修正，保留反例和下一步验证。

主要用户为进入陌生行业的AI产品经理、独立开发者、创业者和研究者。受访者与工具使用者/购买者可能不同，不能混同。

首轮Demo定位“小型创业公司办公”，暂按中国大陆、5—50人知识工作型创业团队界定；它是跨行业人群而非单一垂直行业，此范围待进一步确认。后续按地区、业务类型、规模、岗位和采用阶段分层。

## 2. 成功标准与范围

降低准备和整理成本，让用户获得能执行的计划、能分发的问卷、能核对的场景卡和研究报告。优先现成工具、小轮次证据和低成本验证。

不承诺小样本测出行业总体采用率、市场规模、因果收益或需求真假。需求研究收集支持或反驳的证据；持续使用与付费需要后续验证。

## 3. 用户流程与功能

| 编号 | 用户任务 | 当前实现 | 验收标准 |
| --- | --- | --- | --- |
| FR01 | 定义研究范围 | 新建/切换项目，保存主题、地区、目标群体、截止日期 | 项目隔离，重启可恢复，新行业无预设结论 |
| FR02 | 规划调研 | 默认约10.5小时计划；模型可按行业调整 | 有方法、工时、完成标准和状态，生成不等于执行 |
| FR03 | 搜集知识及专项材料 | 手动录入公开资料、访谈、观察；可选公开搜索 | 有来源、日期、范围、内容和局限；摘要标未核 |
| FR04 | 解读现状与场景 | 模型结构化生成，Demo人工整理 | 每卡含角色、触发、流程、决策、策略、心理、反例、下一步和引用 |
| FR05 | 分析行业与自采数据 | 外部统计口径作为证据；程序计算本样本 | 区分地区、年份、AI定义、分析单位、分母及缺失，不误推总体 |
| FR06 | 生成问卷/访谈材料 | 问卷schema、30分钟提纲、独立HTML表单 | 近期事件问题、匿名及同意参与，能填写、交回和导入 |
| FR07 | 输出报告 | Markdown、可打印HTML、完整项目JSON | 含范围、方法、来源、结论、反例、样本、局限和下一步 |
| FR08 | 自主补证据 | 单Agent选择证据查询、数据分析和可选搜索 | 工具有界、错误可反馈、输出校验失败可有限修正 |
| FR09 | 显示运行状态 | 配置提示及成功工具轨迹，无密钥报错 | 静态/模拟/真实状态明确，不能虚称完成 |

流程：研究简报 → 方法和任务 → 通用资料 → 专项访谈/观察 → 场景与反例 → 问卷回收分析 → 真实任务对比 → 报告与下一轮。允许根据证据缺口往返，不把访谈当必须一次完成的形式步骤。

## 4. 交付物设计

- 公开体验：只读Demo与示例报告，仅含公开种子资料；不触发模型调用。
- 真正研究：本地工作区、证据、问卷、分析与导出，模型/搜索按配置启用。
- 同行分享：GitHub、README、策略说明与白皮书，清楚说明验证程度。
- 全过程备份：完整项目JSON，包含私有原始资料，不等于可公开报告。

当前导出结构固定，尚未按“仅会话判断/只要表单/深度报告”自适应选择载体；此项属于后续候选，不宣称已有。

## 5. 数据与成本约束

问卷仅保存同意参与者。匿名受访者ID重复时拒绝整个追加，不覆盖旧回答。团队数按已知匿名团队ID去重，不代表所有独立企业均已识别。

完整耗时差值＝原方法总耗时－AI流程全部耗时；只纳入质量达标且两项耗时完整的回答，空白保留缺失、负值保留。自报描述不能证明因果收益，个人状态不是企业采用率。

密钥由后端读取，排除发布；项目资料需获准并脱敏，发送模型前由用户确认。默认仅绑定本机，无云端自动回收、多人账号和公网权限隔离。

默认最多6轮模型、3次搜索、每轮8个工具请求、单次6500输出token、单次网络超时45秒，循环间检查240秒时限。次数限制不是货币硬限额，仍可能超过在途请求时限；详见策略。

## 6. 验证状态与下一轮

已通过19项程序/模拟工具循环及内存HTTP路由测试；公开Demo与场景、问卷、报告入口已检查。程序测试覆盖编号、确定性降级、去重、缺失、负节省、转义、持久化、缺密钥、搜索及轮次预算。

尚未完成真实模型/搜索端到端专业验收；没有目标人群真实访谈与问卷，没有任务效果/ROI实测。此前执行环境限制本地端口，内存路由测试不替代真实本地服务验收。

下一轮依次：使用公开资料配置真实模型 → 测正常/缺证据/冲突/故障/停止决策 → 招募4位一线、1位负责人、1位实施者，尽量覆盖3个团队及不同采用阶段 → 取得3—5份获准样例，预定质量标准并测完整耗时 → 泛化badcase再决定扩功能。

专业验收单独记录决策、内容、交付及成本，保留未用于调优的案例；程序通过率不能代替专业通过率。

## 7. 维护约定与变更

使用固定文件名更新，需求改变同步策略、评测及对外说明，与对应可发布实现一起提交；同步用户指定Obsidian目录并校验内容一致，不生成多份“最终版”。
